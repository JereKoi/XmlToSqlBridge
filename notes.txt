hierachial structure management:

	  -> GetProductsResponse -> Products -> Product.

	- XDocument and Descendants on other hand makes it so that I dont need to
	  write complex loops to move from one loop to other. Using LINQ to XML library's
	  descendants method which automatically searches all especifically named elements
	  regardless of how deep in XML tree they are living in. This is very powerful tool,
	  when we have to pick from massive integration text just some specific information.

Namespaces, XNamespace, their meaning and management in SOAP-architecture
	- I learned one of most critical SOAP-world's rule. Why namespaces exist?
	  In integrations and web services, XML-documents can combine different elements
	  from different systems. Name spaces such as xmlns="[http://tempuri.org/]
	  (http://tempuri.org/)" ensure that element name Product, is not mixed with some
	  other system's similarly named element.
	  
	- I learned that C# does not find elements purely based on strings like "Product"
	  if document has only namespace defined. 
	  By creating XNamespace ns ="[http://tempuri.org/](http://tempuri.org/)"; and
	  combining it to element name (ns + "Product"), I tell program exactly in which
	  system that product is searched in.

Defensive programming and null-safety
	- In real life integrations, SOAP-responses are not always in correct format.
	  Some field may be missing or API-provider has changed schema without notifying.
	  Null check operator ?. checks is XML-field is not at all found for specific
	  product. This way if it is missing, program does not crash to NullReference-

	  Businesses use this in daily basis; they take in external, often complex and

Primary Key:
	- Primary key is unique and it makes sure that each row is always unique. Not any other
	  row can share same primary key (perusavain). For example two products cannot have same ID-
	  number. Primary key field cannot be never null. Each row has to be active identifier.
	  Primary key upholds data integrity. Primary key works as last defence. If program or 
	  integration tries to accidentally save existing info again, database stops it
	  automatically, such as Violation of primary key-error. Primary key also improves
	  speed of queries. Database creates automatic indexing around primary key, which 
	  makes searching for data, updating and deleting with specific ID very fast especially when
	  table has millions of rows.

Why duplicate rows are issue?
	- Data goes wrong, wrong raports and calculations. If database has two copies of same product,
	  all statistics and calculations goes wrong. For example warehourse price as whole or product
	  amount shows way too high number.

Business fail and catasthrophies, operational errors:
	- In integrations and webshops, duplicates can in worst scenarion cause situation where
	  customer gets two products, customer is billed twice or system thinks, that there are
	  more than one order. Some tables which have two rows, but data has been updated
	  such as price has been updated, database does not know which row is the right one
	  (single source of truth). Duplicate rows also cause unnecessary resource consumption.
	  Even though hard disks are cheap and in million class system unnecessary duplicate rows
	  cause turbulance in database, which causes queries to be slower and make friction on
	  server's memory. This is why databases have always strict rules, like those PRIMARY KEY,
	  which works as automatic bouncer and stops faulty data to get into party.

Error handling and logging:
	- Try catch block is useful to catch exceptions and errors. Catch block is used to prevent
	  program to not crash if something goes wrong. Logging is used to write what went wrong and when.

Upsert and Merge:
	- Smart data management. Instead of system only adding rows blindly or crash to duplicates,
	  MERGE-clause can check situation on fly and decide itself if it needs to use INSERT or
	  if there is existing row and use UPDATE instead. Solely skipping duplicates would leave
	  old info to live on database. Upsert-model ensures, that for example product price changes
	  on SOAP API, also database price changes automatically to correct one. Integration reapplicability.
	  When database and SQL-clause sort duplicate issue and updates smartly, same integration job can
	  be ran again and again safely without errors or data corruption.

Transactions and rollback:
	- Lets think of situation where SOAP-API sends me at once 100 products and my program starts
	  to save them from list one by one to database. Products 1-49 saving is succesfull. On
	  product 50 is some unexpected error, for example required data is missing or database connectino
	  cuts of momentarily. Without transaction, producst 1-49 would be on database, but rest of 50
	  products end up missing from database. Database is now halfway (half-baked), data is inconsistent.
	  Transaction being all or nothing, either all 100 products are saved succesfully (commit) or
	  even one faulty saving results into error, database rolls back all and not even one
	  data is changed on database. Database remains intact.

How to use transcations in code?
	- In Microsoft.Data.SqlClient-library transaction is started straight away from opening the connection
	  (connection.BeginTransaction()) and it is tied to commands. BeginTransaction is the batch (job).

I deleted necessary info from mock SOAP response, but transcation did not rollback. Why?
	- I did negative test, so deleting necessary info from SOAP-response to see if rollback works.
	  Reason why transaction did not go to error and catch-block didnt activate despite deleting Id
	  and Name from one of products on SOAP-response. Reason lies on these two lines;
	  if (int.TryParse(p.Element(ns + "Id")?.Value, out int id) &&
		int.TryParse(p.Element(ns + "Price")?.Value, out int price))
	  When I deleted Id from SOAP-response, p.Element(ns + "Id")?.Value returned null.
	  int.TryParse(null, out int id) returned false. In human communication it said: "Hey
	  this is not valid whole number"). Because if statement returned false, whole block's
	  code including database command was not performed at all. Program only skipped that
	  specific product unnoticed and went through rest of them in loop and performed
	  transaction.Commit(); to the end. Because faulty data was not even attempted to be
	  saved to database, no exception happened. This raises architectural question,
	  Is it right if SOAP-response is missing data, program only skips product and
	  continues. Maybe sometimes this is on purpose, but often dangerous as errors or missing
	  information was missing without anybody noticing it. Option B strict validation after fail.
	  With option B question is that do I want so that product is missing some critical data such
	  as Id, does program raise alert, throw new exception or rollback whole batch run? I will
	  go with option B, because in enterprise integrations it is used to build quality and 
	  trustworty processing.

What I learned after adding transaction triggering exceptions to code?
	- Adding strict validation (fail fast) to code, instead of my program silently skips
	  ahead when faulty SOAP-response has product that is missing id or whatnot, it immediatly
	  throws exception and catch-block is activated to rollback whole operation. Errors
	  are needed to be known immediatly, so that it is easy to react to them so that faulty
	  data does not spread to database. Atonomic and safety nets (All or nothing). Transaction
	  makes sure that database remains intact. Either all batch data has gone through succesfully
	  (Commit) or even if one product is faulty, all changes are rolledback. Database is never left
	  in half-baked state or messy state. Transactions makes sure that error processing is structured 
	  and safe. When code gets to exception, catch block reacts to this and acts as safety net for
	  database, making sure that data remains intact and leaves to humans log message to react to when
	  something goes wrong.

Commit:
	- Commit means tranasction ending. When program calls transaction.Commit(); it tells database:
	  "All batch products were handled succesfully without any errors. You can now save all changes
	  (additions and updates) entirely to database." Commit () = Accept and save all changes
	  (when everything went alright). Rollback() = Rollback everything (when something went wrong,
	  so that database is not left in half-baked state/some data saved, some data missing).
